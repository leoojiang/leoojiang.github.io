Training a Reward Model from Scratch

Follow the LLM101 training stack from Chinese livestream transcripts and byte-level BPE to a small chat model, a standalone reward scorer, and a DPO-tuned policy.

One tokenizer, three data formats, two final models

I started with a small decoder and used the HuChenFeng livestream archive to teach it a specific interaction pattern: a viewer speaks, then the host answers. The project also has a raw-text corpus and a separate preference-pair file. Each format carries a different training signal.

Where the data came from

Raw text for the tokenizer and base model

pretrain.jsonl supplies an unstructured text field per row. LLM101 has scripts to tokenize it and train on it. The checkout contains the processed corpus but does not record its upstream source. The HuChenFeng archive is the documented source for the dialogue conversion below.

HuChenFeng viewer–host turns for SFT

I used Olcmyk/HuChenFeng, a month-organized archive of livestream transcripts. convert_hcf_sft.py scans Markdown files, normalizes whitespace, retains lines starting with 某网友： or 户晨风：, and pairs adjacent viewer → host turns among the retained lines. The character filters are 6–150 for viewer text and 10–320 for host text. These are cheap noise filters. Check the 512-token budget after chat formatting as well.

{"messages":[{"role":"user","content":"Convert 2.5 hours to minutes."},{"role":"assistant","content":"Multiply by 60: 150 minutes."}]}

This invented example shows the schema. The host's real response supplies a demonstration of conversational behavior. It may contain transcription mistakes or subjective claims, so review examples and split by episode if you want to measure generalization to unseen broadcasts.

Chosen and rejected answers for RM and DPO

A viewer–host exchange supplies one observed answer. To make a preference pair, generate or write another plausible answer to the same prompt and label both against a rubric. For a factual task, prioritize correctness, then adherence to the requested format, then clarity. Blind candidate order, record why one wins, and keep unresolved ties out of a strict binary trainer. The pilot used the existing local dpo.jsonl. Its upstream provenance is unrecorded in this checkout.

{"prompt":"Convert 2.5 hours to minutes.","chosen":"150 minutes.","rejected":"125 minutes."}

The RM script accepts the flat format and compatible two-turn conversational pairs. It skips empty or token-identical answers and overlong pairs, then hashes the normalized prompt into 90/5/5 train, validation, and test buckets. For archival dialogues, group near-duplicates and source episodes before splitting to limit leakage beyond identical prompts.

Byte-level BPE and the .bin file

train_tokenizer.py reads the first 200,000 text rows at most. It starts from the byte alphabet and learns frequent adjacent-symbol merges up to a 6,400-token vocabulary. The saved tokenizer.json holds the vocabulary, merge rules and byte-level encoder/decoder configuration. It reserves <|endoftext|>, <|im_start|>, and <|im_end|>. The local tokenizer encodes 你好 as token ID 3193, an example of a frequent byte sequence becoming one token.

prepare_data.py encodes every pretraining row, appends the end-of-text ID and writes the IDs in chunks. The vocabulary fits in uint16. The local file is 632,817,122 bytes, or 316,408,561 token IDs including separators. There are no JSON records in the binary stream. NumPy memmap lets the trainer read random windows without loading the entire file into memory. A training window can span documents; the separator remains in the sequence.

SFT, RM and DPO use the same tokenizer but preserve JSONL boundaries so each loader can render the chat roles and identify exactly which text is a prompt, a target or a candidate.

Why the transcript goes to SFT

Pretraining teaches the base decoder to predict the next token over a broad text stream. Here a random 512-token window is paired with the same window shifted one position forward. SFT takes the pretrained weights and changes the supervision: the viewer prompt remains visible as context, while the loss is restricted to the host's answer and its end marker.

Flattening a transcript into pretraining text would also train the model to predict viewer messages and archive formatting. That can be useful for domain adaptation. For this exercise, the role boundaries already give us a precise objective: given what the viewer said, learn what an assistant response looks like. SFT keeps those boundaries and avoids spending the response-training loss on the viewer turns.

Inside MiniModel

The saved checkpoint uses a decoder-only Transformer with 8 blocks, width 512, 8 attention heads of 64 channels each, and a 512-token context. Each block uses pre-normalization and two residual connections.

Pretraining, SFT and DPO use a vocabulary head tied to the input embedding matrix. It maps each hidden state to 6,400 logits. That head supports generation and next-token likelihood. RM reuses the backbone but reads a different output: it pools the hidden state at the last real token and projects 512 channels to a single score.

RM scores two answers with one shared model

The Bradley–Terry objective models the probability of choosing the preferred answer as σ(r⁺ − r⁻). A zero-initialized head gives margin 0 and loss log(2) ≈ 0.693 before the first update. If the two scores were 1.2 and 0.4, the margin would be 0.8 and the modeled preference probability about 69%. That is an illustration; real probabilities require calibration checks.

LLM101 fine-tunes the backbone and new head with AdamW and selects the checkpoint by validation loss. Right padding never becomes the pooled token. The causal mask keeps future pad positions out of the selected representation.

Run LLM101

Run these commands from the project root in a Python environment with PyTorch and tokenizers. The existing SFT and DPO scripts expect CUDA. The RM script also supports CPU, which is useful for a tiny smoke test. The example uses the project’s existing tokenizer and pretrained MiniModel checkpoint. To prepare your own corpus, place the SFT and preference exports in the paths below.

Build the tokenizer and pretrain the base model

Place the raw-text JSONL under dataset/mini/. The tokenizer trainer writes at the repository root, while the trainer and binary converter load from out/mini/. The copy below connects those paths.

python scripts/train_tokenizer.py
New-Item -ItemType Directory -Force out/mini
Copy-Item tokenizer.json out/mini/tokenizer.json
python scripts/prepare_data.py
python scripts/train_pretrain.py

Convert transcripts and run post-training

Clone the archive, point SRC_DIR in scripts/convert_hcf_sft.py to that checkout, and run python scripts/convert_hcf_sft.py. If you already have the trained tokenizer and pretrain.pt, start here. Before training DPO, export its train split to dpo_train.jsonl.

python scripts/train_sft.py --data dataset/mini/hcf_sft.jsonl --ckpt pretrain.pt --out-name sft_hcf.pt

python scripts/train_rm.py --data dataset/mini/dpo.jsonl --tokenizer out/mini/tokenizer.json --init out/mini/sft_hcf.pt --output out/mini/reward.pt --epochs 1 --batch-size 8 --lr 1e-5

python scripts/train_dpo.py --data dataset/mini/dpo_train.jsonl --ckpt sft_hcf.pt --out-name dpo.pt

For a shared RM and DPO evaluation, build dpo_train.jsonl from the same 90% train bucket. Normalize each prompt with " ".join(prompt.casefold().split()), take the first eight hex digits of its SHA-256 digest, convert them to an integer, and keep rows whose integer modulo 100 is below 90. Keep held-out prompts out of SFT as well. For separate experiments, the DPO script accepts any compatible training export.

Evaluate and fine-tune

  1. Smoke-test one run with examples in every split. Confirm the best checkpoint reloads and each score margin is finite. A zero-initialized score head starts at zero margin and about 0.693 pairwise loss.
  2. Overfit a small training subset and check that the chosen scores move above the rejected scores. If they move in the opposite direction, inspect label orientation and response ordering before tuning hyperparameters.
  3. Compare validation pairwise accuracy and loss against a length-only baseline. Slice by task, candidate source and response-length gap. Inspect short correct answers paired with long plausible mistakes.
  4. Fine-tune for a few epochs from the same SFT checkpoint and compare validation loss across learning rates, keeping the split and seed fixed. For continual tuning from a saved RM, restore the full reward_model state into the scorer and use fresh validation data. The CLI’s --init takes a MiniModel checkpoint.
  5. Once you select the configuration, evaluate on held-out prompts and report sample counts and uncertainty. For reranking, evaluate the actual candidate pool and compare the top-scoring answer with a human-reviewed baseline.

What the pilot established

I sampled 512 rows from the local preference corpus with seed 42. Filtering left 169 train pairs, 21 validation pairs, and 16 test pairs. After one epoch, the checkpoint got 12/21 validation pairs and 7/16 test pairs correct. Test loss was 0.6934, close to the equal-score baseline of 0.6931. The run verifies the pipeline and checkpoint reload. The small test set gives no convincing evidence of ranking quality.

Raw rewards are relative scores. Use the score gap to compare two answers to the same prompt. Calibrate separately on held-out labels if a downstream consumer needs a reliable probability.

How DPO uses the same preference pair

Initialize a trainable policy π and a frozen reference πref from sft_hcf.pt. The DPO loader scores the chosen and rejected responses with both models, summing shifted log probabilities over assistant tokens. This gives four log probabilities per pair.

gain_chosen   = log π(chosen | prompt)   − log π_ref(chosen | prompt)
gain_rejected = log π(rejected | prompt) − log π_ref(rejected | prompt)
Δ_DPO         = β × (gain_chosen − gain_rejected)
loss          = −log σ(Δ_DPO)

LLM101 defaults to β = 0.1. At initialization, policy and reference coincide, so their log-probability differences are zero. Training pushes the chosen response's gain over the reference above the rejected response's gain. The runner saves a generative dpo.pt checkpoint. It never needs to load reward.pt.
